# nodl_runtime_py

`nodl_runtime_py` provides what Python code generated by `nodl_generator_py` needs at runtime:
its runtime dependencies, `LifecycleNode`, a lifecycle node base class, and `run_node`, a main loop for `rclpy` nodes.

A package that generates Python nodes declares the generator as a build tool and this package as a runtime dependency,
the way message packages pair `rosidl_default_generators` with `rosidl_default_runtime`:

```xml
<buildtool_depend>nodl_generator_py</buildtool_depend>
<exec_depend>nodl_runtime_py</exec_depend>
```

`nodl_generate_py()` fails at configure time when the calling package does not declare it.

## What it provides

| Dependency | Why generated code needs it |
|---|---|
| `rclpy` | Generated base classes derive from `rclpy` node classes and create their entities. |
| `generate_parameter_library_py` | Generated parameter modules import its parameter validators. |

The list may change as generated code changes, so depend on this package rather than on its contents.

## LifecycleNode base class

`nodl_runtime_py.lifecycle.LifecycleNode` derives `rclpy.lifecycle.LifecycleNode` to provide a more opinionated and automated default behavior.
It implements and seals the standard lifecycle callbacks (`on_configure`, `on_activate`, `on_deactivate`, `on_cleanup`, `on_shutdown` and `on_error`),
so that the standard management of `rclpy` for lifecycle publishers and other managed entities always runs.
A subclass adds behavior by overriding the hooks `handle_configure`, `handle_activate`, `handle_deactivate`, `handle_cleanup`, `handle_shutdown` and `handle_error`.
Each hook takes the previous `LifecycleState`, returns a `TransitionCallbackReturn`, and defaults to SUCCESS.

A subclass that defines an `on_*` callback raises a `TypeError` when the class is defined, and the message names the hook to define instead.
The callbacks are also marked `@final`, so that `pyright` reports an override.
The generated Python base of a document that includes `nodl://nodl_common_interfaces/lifecycle_node` derives this class.
An authored implementation of the generated node defines the same hooks.

### State transitions

| Transition | Order |
|---|---|
| configure | hook only |
| activate | standard activation, then hook. A result other than SUCCESS or an exception runs the standard deactivation |
| deactivate | hook, then if the hook returned SUCCESS the standard deactivation |
| cleanup | hook only |
| shutdown from active | `handle_deactivate`, standard deactivation, then `handle_shutdown` |
| error from active | `handle_deactivate`, standard deactivation, then `handle_error` |
| shutdown or error from unconfigured or inactive | hook only |

Some behavior specifics:

- The standard activation activates the lifecycle publishers, so `handle_activate` runs with them active and `handle_deactivate` runs with them still active.
- On shutdown and error from the active state `handle_deactivate` runs first, so custom logic such as stopping timers runs on every path that leaves the active state.
- A shutdown cannot be vetoed, so a result other than SUCCESS from `handle_deactivate` on these paths is logged and ignored, an exception from it is logged, and the shutdown or error hook runs regardless.
- An error that `handle_deactivate` caused by raising does not run it again.
- A failed or raising `handle_activate` does not run `handle_deactivate`, and leaves the lifecycle publishers inactive.
- A failing `handle_deactivate` leaves the node active.
- Create timers last in `handle_activate`, so that a failing hook leaves none of them firing.
- A hook that raises is turned into ERROR by `rclpy`, which runs `on_error`.
  The exception itself is not logged by `rclpy`, so log it in the hook when it matters.
- When `handle_error` returns SUCCESS, the node ends unconfigured.

### Background

`rclpy.lifecycle.LifecycleNode` activates its lifecycle publishers and other managed entities in its default `on_activate`, and deactivates them in `on_deactivate`.
A subclass that overrides those callbacks without calling the base class leaves them inactive.
Sealing the transition callbacks and offering hooks instead makes that standard behavior impossible to skip.

## Running a node

`run_node` is the main loop of an executable.
It constructs the node, spins it, and returns the process exit code.
An executable module returns it from `main()`, so a `console_scripts` entry point and running the module directly both exit with it:

```{literalinclude} examples/greeter.py
:language: python
:start-at: import sys
```

The node class is called with no arguments.
`run_node` returns 0, so the process exits with 0, when it receives SIGINT or SIGTERM, or when `rclpy.shutdown()` is called, from the node or from any thread.
A second signal restores the default behaviour, so a process stuck in a constructor, a callback or a shutdown can still be interrupted:
a second SIGINT raises `KeyboardInterrupt`, and a second SIGTERM terminates the process.
`run_node` installs signal handlers, so it must be called from the main thread, and raises `RuntimeError` otherwise.
The signal handlers that were installed before the call are restored when it returns.

### Lifecycle nodes

A lifecycle node is configured and activated after construction.
A transition that does not succeed raises a `RuntimeError` naming the node and the transition.
On exit the node is shut down, so that its `handle_shutdown` hook runs, or its `on_shutdown` callback for a node that derives `rclpy.lifecycle.LifecycleNode` directly.
This does not happen when `rclpy.shutdown()` was called first, because the transition cannot be published.

### Errors

Exceptions from the constructor, a lifecycle transition or a callback propagate to the caller, so the process exits with a traceback and a non-zero code.
Before they propagate, `run_node` shuts down the executor, shuts down a lifecycle node, destroys the node, and shuts down `rclpy`.
A cleanup step that fails does not skip the others.
When another error is propagating, the failures are logged.
Otherwise the first one is raised and any others are logged.

### Choosing the executor

Nodes are spun with a `SingleThreadedExecutor` by default.
Pass any executor class that takes no arguments as `executor_class`.
This executable reuses the `Greeter` example above:

```{literalinclude} examples/greeter_multithreaded.py
:language: python
:start-at: import sys
```

### Command line arguments

`run_node` passes `args` to `rclpy.init`, `sys.argv` by default, so ROS arguments such as `--ros-args -p greeting:=Goodbye` work as usual.
When passing `args`, put the program name first, as `sys.argv` does.
